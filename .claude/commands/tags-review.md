# Tags Review

Walks the pending rows of `.todos/0000-tags-review-journal.md` — generated by `tags review`
(`.scripts/tags-manager.py` → `scripts/tags-review.mjs`, which calls Ollama via
`scripts/suggest-tags.mjs` against the real `blog/tags.yml` catalogue) — with the author, and
applies the tag changes they accept.

This command doesn't call Ollama or write to `tags` frontmatter directly itself — that's
`tags review` (for suggestions) and `tags set-tags` (for the write), both invoked as
subprocesses. Step 1 below runs `tags review` to refresh the journal (cheap once it already
exists — only new or `blog/tags.yml`-stale articles trigger an Ollama call) before selecting
what to review, so new articles never need a separate manual step.

## 0. Parse arguments

Read `$ARGUMENTS`.

- Empty → `BATCH_SIZE = 15`
- A single integer → `BATCH_SIZE = that number`, hard cap 30. Above that, stop and print:
  `Usage: /tags-review [batch-size]  Example: /tags-review 10` — past ~30 in one sitting this
  stops being a genuine per-article look and becomes rubber-stamping.
- Anything else → treat it as one article (path, folder, or slug): resolve it by slug in the
  journal and review just that row, ignoring `BATCH_SIZE`.

## 1. Refresh the journal

```bash
test -f .todos/0000-tags-review-journal.md
```

- **Missing entirely** (first ever use): stop and tell the author to run `tags review`
  themselves first — a cold run calls Ollama once per article in the whole corpus, so it can
  take a while; suggest running it in the background. Do not launch this bootstrap run
  yourself from inside the command.
- **Already exists**: run it now, before selecting the batch —

  ```bash
  python3 .scripts/tags-manager.py review
  ```

  This is what picks up articles written since the last session: new articles get a fresh
  suggestion, everything already in the journal is left untouched (cheap — no Ollama call for
  a row that already exists and is still current). If `blog/tags.yml` changed since the last
  run, the script detects it and refreshes every row instead — mention that to the author if
  it happens, since it means today's batch may include rows that were already reviewed
  before.

## 2. Load the journal and select the batch

Read `.todos/0000-tags-review-journal.md`. Parse its table: `| Revu | Slug | État | Tags
actuels | À ajouter | À retirer | Notes |`.

Rows with an empty `Revu` (`—`) are pending. Take the first `BATCH_SIZE` of them, in the
order they appear (that order is the corpus's chronological folder order — oldest first).

If there are none, report **"Nothing to review — the journal is fully caught up."** and stop.

**Tell the author upfront**: a compact table of the selected slugs with État, Tags actuels,
and the suggested À ajouter / À retirer, before touching anything.

## 3. Review each article with the author

For each selected row, one at a time, the decision **MUST** be collected with the
`AskUserQuestion` tool — never as a plain-text question. The author wants a click/tap choice
every time, not a sentence to type back; this is a hard requirement of this command, not a
per-session preference to re-derive.

Before calling it, show the slug, État, current tags, and the model's suggested
additions/removals as plain text (a short table or a few lines is fine) — `AskUserQuestion`'s
own question text is not the place for that detail. Then call `AskUserQuestion` with exactly
these four options (`multiSelect: false`):

1. **Accepter la suggestion** — final tags = tags actuels ∪ à ajouter, minus à retirer.
2. **Garder tel quel** — ignore the suggestion, tags unchanged.
3. **Passer** — leave the row pending, come back to it later (does not count as reviewed).
4. **Arrêter la session ici** — stop the batch now; do not ask about further rows.

A hand-picked subset or a different final list is still possible — the tool always offers a
free-text "Other" choice; treat that text as the final tag list (comma-separated) rather than
re-prompting.

If the author picks "Arrêter la session ici" on any row: stop asking immediately, skip
straight to step 6 (session report) covering only the rows actually resolved so far, and do
not touch the row currently being asked about (leave it pending).

Do not batch multiple rows into one question and do not add an "accept all" shortcut — one
`AskUserQuestion` call per row, every row, is the point of this command.

## 4. Apply an accepted decision

When the final tag list differs from what's on disk, resolve the article's file:

```bash
find blog .unpublished -path "*/<slug>/index.md" -o -path "*/<slug>/index.mdx" 2>/dev/null | head -1
```

Then:

```bash
python3 .scripts/tags-manager.py set-tags <file> "tag1,tag2,tag3"
```

This writes `tags: [tag1, tag2, tag3]` (forced flow style) and normalizes an old block-style
list on the way. Never hand-edit the `tags:` line — always through `set-tags`, so every
article's tags stay in the same format.

## 5. Update the journal row

For every row resolved this session (accepted, tweaked, or explicitly kept unchanged — **not**
skipped), rewrite its line immediately, right after that article's decision — not batched to
the end, so a session that stops partway through loses nothing already decided:

```text
| YYYY-MM-DD | <slug> | <état> | <final tags, comma-separated> | — | — | <note> |
```

- `À ajouter` / `À retirer` become `—`: the suggestion has been acted on, so leaving the old
  values would read as still-pending the next time someone opens the file.
- `Notes`: a short trace of the decision — `"ajouté: docker, python"`, `"retiré: excel"`,
  `"gardé tel quel"`.

## 6. Session report

A table of everything processed this run:

| Slug | Décision | Notes |
| ---- | -------- | ----- |
| ... | appliqué / gardé tel quel / passé | ... |

Then: "N article(s) restent à traiter — relance `/tags-review` pour continuer."

If the journal is now fully caught up, say so — the next `/tags-review` will still refresh it
first (step 1), so an article written between now and then is picked up automatically without
any manual step.
